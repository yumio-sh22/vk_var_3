## 2. Источники и способы сбора

| Источник | Тип (поток / batch / CDC / документы / API) | Способ сбора |
|---|---|---|
| `documents/regulation.pdf` | Документ PDF, batch | Файл считывается из локальной папки `documents/`. `ingest.py` извлекает текст постранично с помощью `pypdf`. Batch выбран потому, что регламенты загружаются и переобрабатываются при появлении или изменении файла, а не поступают непрерывным потоком. |
| `documents/instruction.docx` | Документ DOCX, batch | Файл считывается из той же папки. `ingest.py` извлекает текст из абзацев и таблиц с помощью `python-docx`, сохраняя сведения о разделе. |
| Вопрос сотрудника | Текстовый запрос, online / по требованию | Вопрос передается при запуске `generate.py` из командной строки. Для него создается embedding, затем выполняются векторный и полнотекстовый поиск; найденный контекст передается генеративной модели. |

В этой реализации документы поступают из локальной папки проекта. Для корпоративного варианта источником может быть общее хранилище регламентов, из которого файлы копируются или синхронизируются в зону ingestion. Потоковая обработка и CDC для данного сценария не требуются: исходные данные являются документами, которые обрабатываются пакетно.

**Контур подготовки документов (Offline / Batch):**

1. PDF и DOCX поступают из папки с документами.
2. Ingestion извлекает текст и доступные метаданные, выполняет проверку и подготовку содержимого.
3. Chunking разбивает текст на смысловые фрагменты, сохраняя сведения об исходном документе, странице или разделе.
4. Embedding-модель `nomic-embed-text` преобразует фрагменты в векторы размерностью 768.
5. Текст, метаданные и векторы сохраняются в PostgreSQL с расширением pgvector.

**Контур обработки вопроса (Online):**

1. Сотрудник передает вопрос на естественном языке.
2. Для вопроса создается embedding; параллельно выполняется полнотекстовый поиск.
3. PostgreSQL использует векторный индекс HNSW и полнотекстовый индекс GIN.
4. Результаты объединяются методом RRF.
5. Из найденных фрагментов формируется контекст для Ollama / `gemma4:e4b`.
6. Сотрудник получает ответ с указанием исходного документа. Если в документах нет нужных сведений, модель должна сообщить о недостатке информации.

На схеме также показан контур оценки качества поиска: контрольные вопросы с заранее определенными релевантными документами, сравнение методов и расчет метрик. В легенде разделены источники, подготовка, векторное хранение, поиск, контекст, LLM и оценка.

В фактическом запуске роль хранилища источников выполняет локальная папка `documents/`; блок корпоративного хранилища на схеме показывает, откуда документы могли бы поступать в целевой корпоративной системе.

docker compose exec ollama ollama list

Дополнительные фактические проверки:

- `vector` — версия `0.8.7`;
- таблицы `documents` и `chunks` существуют;
- после удаления старых демонстрационных записей в базе осталось 2 актуальных документа и 2 фрагмента;

## 5. Описание

| Шаг | Для чего | Результат |
|---|---|---|
| 1. Получение документов и извлечение текста | Получить документы и извлечь из них текст. Для PDF используется `pypdf`, для DOCX - `python-docx`. | Текст документов и сведения об исходном файле, странице или разделе. |
| 2. Разбиение на фрагменты | Разбить текст на смысловые фрагменты, чтобы не передавать целый документ модели и точнее находить нужное содержание. В настройках обработки использованы фрагменты примерно до 1200 символов с перекрытием около 180 символов. | В текущем корпусе получено 2 фрагмента, по одному из каждого документа. |
| 3. Векторизация текста | Преобразовать каждый фрагмент в числовой вектор с помощью `nomic-embed-text` через Ollama. | Получено 2 вектора размерностью 768; их наличие проверено в PostgreSQL. |
| 4. Хранение и индексация | Сохранить документы в `documents`, а фрагменты, метаданные, текст и векторы — в `chunks`. Создать индексы для разных способов поиска. | PostgreSQL + pgvector; HNSW для векторного поиска по cosine distance, GIN для полнотекстового поиска. |
| 5. Поиск информации | Преобразовать вопрос пользователя в embedding, выполнить векторный и полнотекстовый поиск, объединить ранги через RRF. | Получен упорядоченный список фрагментов-кандидатов с указанием файла и страницы/раздела. |
| 6. Генерация | Передать вопрос и найденный контекст модели `gemma4:e4b` через Ollama. Попросить отвечать на основании контекста и указывать источник. | Сформирован ответ с названием исходного документа; при недостатке сведений проверен отказ от ответа. |
| 7. Оценка качества | Сравнить векторный, полнотекстовый и гибридный поиск на контрольных вопросах с заранее известными релевантными документами. | Рассчитаны Precision@1, Precision@2, Recall@2, MRR и nDCG@2. Ограничения набора указаны ниже. |

### Результаты первичной оценки поиска

Первичный запуск `evaluate.py` выполнялся на контрольном наборе из 6 вопросов и двух первоначальных демонстрационных документов (`demo_regulation` и `demo_instruction`). Для каждого вопроса был задан один релевантный документ. Средние макро-метрики из фактического вывода программы:

| Метод | Precision@1 | Precision@2 | Recall@2 | MRR | nDCG@2 |
|---|---:|---:|---:|---:|---:|
| Векторный | 1.000 | 0.500 | 1.000 | 1.000 | 1.000 |
| Полнотекстовый | 0.667 | 0.333 | 0.667 | 0.667 | 0.667 |
| Гибридный (RRF) | 1.000 | 0.500 | 1.000 | 1.000 | 1.000 |

На этом контрольном наборе векторный и гибридный поиск во всех шести случаях поставили релевантный документ на первое место. Полнотекстовый поиск не нашел совпадения для двух переформулированных русскоязычных запросов. Это связано, в частности, с тем, что для `search_vector` используется конфигурация PostgreSQL `simple`, которая не выполняет русскую морфологическую нормализацию.

Отдельно проверен вопрос «Как оформить командировку в Японию и какой лимит расходов установлен?». В текущих документах ответа нет. Векторный поиск возвращал ближайшие фрагменты-кандидаты, полнотекстовый поиск не находил совпадений, а `gemma4:e4b` выдала: «В найденных документах недостаточно информации, чтобы ответить на вопрос».

### Роль Data Engineer

Data Engineer отвечает за получение PDF и DOCX, извлечение и очистку текста, разбиение на фрагменты, сохранение метаданных, генерацию и проверку embeddings, организацию хранения в PostgreSQL, создание индексов, реализацию поиска и проверку качества retrieval. Также важно отслеживать актуальность документов: при переименовании файла ingestion воспринимает его как новый источник, поэтому старую запись и её фрагменты нужно отдельно деактивировать или удалить, если документ больше не актуален. В ответственность Data Engineer не входит обучение LLM с нуля, изменение весов gemma4:e4b, создание самой языковой модели и утверждение содержания корпоративных регламентов. Модель используется как готовый компонент для генерации ответа по переданному контексту.

## 6. Вывод

В практической работе спроектирован и проверен RAG-пайплайн для поиска информации в документах PDF и DOCX. Для хранения используется PostgreSQL с pgvector; для поиска - HNSW, полнотекстовый индекс GIN и объединение результатов методом RRF. Для векторизации и генерации ответов используются локальные модели Ollama `nomic-embed-text` и `gemma4:e4b`.

Проверка показала, что система находит нужный документ по прямому и переформулированному вопросу, формирует ответ с указанием источника и отказывается отвечать, когда нужной информации в документах нет. Первичный тест метрик показал хорошие результаты векторного и гибридного поиска на небольшом контрольном наборе. 

В ходе работы отдельно проверены сохранность данных PostgreSQL и моделей Ollama после пересоздания контейнера, а также наличие расширения pgvector и пяти индексов.
